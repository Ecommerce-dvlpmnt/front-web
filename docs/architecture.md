# Архитектура Front Web

## Назначение

`front-web` — клиентская часть интернет-магазина. Frontend отображает страницы,
собирает действия пользователя и обращается к .NET API. Он не должен дублировать
бизнес-правила backend и не должен обращаться к базе данных напрямую.

```text
Пользователь
    ↓
Next.js App Router
    ↓
слой API frontend (src/lib/api)
    ↓
.NET API
    ↓
база данных и бизнес-логика
```

## Базовые принципы Next.js

- Используем App Router и маршруты внутри `src/app`.
- Компоненты являются Server Components по умолчанию.
- `"use client"` добавляется только для интерактивности: state, event handlers,
  browser APIs или клиентских библиотек.
- Первичные данные страницы по возможности загружаются на сервере.
- Переходы между страницами делают через `next/link`, изображения — через
  `next/image`.
- Loading, error и empty-состояния являются частью каждой страницы, которая
  загружает данные.

## Сезонный контент и темы

Текущий первый сценарий магазина — новогодняя коллекция. Сезонные тексты, промо,
заголовок каталога и похожие настройки хранятся в `src/lib/config/shop.ts`:

```ts
shopConfig.seasonal.title
shopConfig.seasonal.catalogTitle
shopConfig.seasonal.announcement
```

Компоненты должны оставаться универсальными. Например, `HeroBanner` может
показывать новогоднюю коллекцию сейчас, но в нём не должно быть архитектурной
зависимости от слова «Новый год». При смене сезона меняются конфигурация и данные,
а не названия компонентов и структура feature-папок.

Переключатель темы находится в `src/components/layout/ThemeToggle.tsx`.
Он переключает класс `.dark` на `html` и сохраняет выбор в `localStorage`. Цвета
интерфейса берутся из токенов `src/app/globals.css`, поэтому новые компоненты не
должны строиться на случайных `bg-white`, `text-black` и других цветах, которые
ломают тёмную тему.

При добавлении UI нужно проверить:

- светлую тему;
- тёмную тему;
- сохранение темы после обновления страницы;
- читаемость текста и видимость focus-состояний в обеих темах.

## Планируемая структура

```text
src/
  app/
    (store)/
      page.tsx                    # главная магазина
      catalog/page.tsx            # каталог
      products/[slug]/page.tsx    # карточка товара
      cart/page.tsx               # корзина
      checkout/page.tsx           # оформление заказа
    (account)/
      login/page.tsx
      account/page.tsx
    layout.tsx
    globals.css
  components/
    ui/                           # Button, Input, Dialog и т.п.
    layout/                       # Header, Footer, ThemeToggle
    home/                         # Hero и блоки главной страницы
    shared/                       # ProductCard, Price, Pagination
  features/
    catalog/                      # фильтры, сортировка, каталог
    cart/                         # состояние и UI корзины
    auth/                         # формы входа и регистрации
    checkout/                     # адрес, доставка, заказ
  hooks/                          # только действительно общие client hooks
  lib/
    api/                          # клиент .NET API и обработка ошибок
    config/                       # чтение и проверка env
    formatters/                   # цены, даты, статусы
    utils.ts
  types/                          # DTO, enums и frontend-модели
```

Папки создаются по мере появления соответствующей функциональности. Не следует
складывать весь код в `components` или делать один большой `page.tsx`.

## Интеграция с .NET API

Все запросы к backend проходят через `src/lib/api`. Компоненты не должны содержать
разрозненные вызовы `fetch` с повторяющимися URL, заголовками и обработкой ошибок.

Рекомендуемая схема:

```text
Server Component / Route Handler
    → src/lib/api/server.ts
    → API_URL
    → .NET API
```

Прямой вызов из Client Component разрешается только когда он нужен для интерактивного
сценария. Тогда используется `NEXT_PUBLIC_API_URL`, backend должен разрешать origin
frontend через CORS, а в браузер нельзя отправлять секреты.

До реализации конкретного экрана нужно согласовать с backend:

- URL и HTTP-метод endpoint;
- формат успешного ответа и ошибок;
- пагинацию, фильтры и сортировку;
- формат денег, валюту и даты;
- авторизацию и обновление сессии;
- правила CORS и cookies.

Предполагаемые домены API: `products`, `categories`, `cart`, `orders`, `auth`.
Это рабочая группировка, а не окончательный контракт — названия должны совпадать
с реальным .NET API.

## Авторизация и данные пользователя

Рекомендуемый вариант — HTTP-only cookie-сессия, управляемая backend. Access token
не следует хранить в `localStorage` без отдельного согласования требований
безопасности. Если .NET API использует другой протокол, его нужно описать в README
и в слое `src/lib/api`, а не реализовывать по-разному в разных компонентах.

## Состояние

- Серверные данные каталога и товара остаются серверными данными.
- Локальное UI-состояние (открыта ли корзина, выбранный фильтр, шаг checkout)
  хранится рядом с feature.
- Состояние корзины и пользователя не должно дублироваться в нескольких независимых
  местах.
- Библиотеку глобального состояния добавляем только после появления реальной
  потребности и согласования.

## Стили и компоненты

- Сначала переиспользуем компоненты из `src/components/ui`.
- Общие компоненты не должны знать о конкретном endpoint.
- Feature-компонент может собирать UI и данные своей области.
- Не добавляем большие UI-библиотеки или новые зависимости без объяснения причины.
- У каждого интерактивного элемента должны быть keyboard/focus-состояния и понятный
  accessible name.

## Этапы реализации

1. Согласовать API-контракты и auth-модель с backend.
2. Собрать shell магазина: layout, header, footer, навигацию и тему.
3. Подключить каталог и карточку товара.
4. Добавить корзину и пересчёт итогов через backend.
5. Добавить checkout, заказ и состояния ошибок.
6. Добавить аккаунт пользователя и полировать responsive/accessibility.

На каждом этапе должен существовать рабочий экран с loading, error и empty-
состояниями, а не только набор заготовленных компонентов.
